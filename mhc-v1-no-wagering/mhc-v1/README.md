# Maternal Health Companion — v1

MHC turns a user's own health entries (text, voice, file) into three
concrete outputs — a report, an appointment prep sheet, and an advocacy
letter draft — generated by an LLM, plus a principal-protected yield vault
and a read-only prediction-market info feed. It's built to be distributed
and account-managed through the **OKX AI Marketplace**, not as a standalone
app with its own signup funnel — that's the piece everything else here is
built around, so it's worth understanding first.

## Architecture

Two independently deployed pieces share one Postgres database:

```
                 ┌───────────────────────────────────┐
                 │         OKX AI Marketplace         │
                 │  (ASP listing = the real account   │
                 │   layer: discovery, billing, auth)  │
                 └───────────────┬────────────────────┘
                                  │ A2MCP calls
                                  ▼
┌───────────────────┐   HTTP    ┌────────────────────────────┐
│  frontend/        │◄─────────►│  backend/                  │
│  Next.js (Vercel)  │           │  Express API (Railway)     │
│  - landing page +  │           │  - /users   (email OTP)    │
│    no-wallet demo  │           │  - /ingest  (entries)      │
│  - bare-bones      │           │  - /generate (report/prep/ │
│    /dashboard for  │           │     letter, via llmClient) │
│    testing only    │           │  - /predictions (read-only)│
└────────────────────┘           │  - /anchor  (stub, 501)    │
                                  │  - /demo, /stats           │
                                  └──────────┬─────────────────┘
                                             │
                       ┌─────────────────────┼─────────────────────┐
                       ▼                     ▼                     ▼
                ┌─────────────┐     ┌─────────────────┐   ┌──────────────────┐
                │  Postgres   │     │  Polymarket      │   │  Shared Agentic  │
                │  (Railway)  │     │  gamma API       │   │  Wallet (OKX     │
                │  users,     │     │  (public, cached  │   │  OnchainOS)      │
                │  entries,   │     │  30 min)          │   │  - Aave v3 on    │
                │  reports,   │     └──────────────────┘   │    X Layer       │
                │  letters,   │                            │  - shared with   │
                │  vaults,    │                            │    AgentPress    │
                │  yield_pool │                            └──────────────────┘
                └─────────────┘
```

**Why OKX is the important piece:** the web app you see (landing page +
`/dashboard`) is a thin, mostly-for-testing surface. The intended primary
surface is the ASP (Agent Skill Package) listing on OKX AI Marketplace,
which acts as the actual account layer — discovery, sign-up, and billing
happen there, not in this app's own auth. Once the ASP is registered, OKX's
**A2MCP handler** calls straight into the same `src/services/*` functions
that `/generate/*` already uses (`reportService.js`, `letterService.js`,
`prepService.js`), so there is exactly one implementation of the report/prep/
letter logic regardless of whether a request came from the web dashboard or
from an agent session on OKX. `/users/session` (email-in, cookie-out) is a
placeholder account system that exists only so the web dashboard is testable
before the ASP listing goes live — it is not meant to be the long-term
identity system.

The vault and yield-harvesting flow (`vaultService.js`, `walletClient.js`)
runs on the same **shared Agentic Wallet** that OKX OnchainOS provisions,
on X Layer, using Aave v3 for yield. That wallet is shared with AgentPress,
so every transaction is tagged `source: 'mhc'` in the ledger to keep the two
products' books separable. Contract addresses (the Aave v3 pool, the USDT
token) are pulled from a hardcoded allowlist in `walletClient.js`, never
from a request — this is deliberate: a wallet that can move funds should
never accept an address as user input. Principal deposited here is always
withdrawable; only harvested yield is ever moved, and nothing in this app
wagers it — see "What v1 does and doesn't do" below.

Prediction-market info (`/predictions/info`) is unrelated to the wallet or
vault: it's a one-way, unauthenticated read from Polymarket's public gamma
API, cached in Postgres for 30 minutes, returned with an explicit
"informational only, not financial advice" disclaimer.

## Request lifecycle (web dashboard path)

1. User enters email at `/users/session/request` → a 6-digit code is
   emailed (`emailClient.js`) and stored hashed, expiring in 10 minutes.
2. User submits the code to `/users/session/verify` → on match, a
   session cookie is issued and a `users` row is created if new.
3. Entries go in via `/ingest`. `/generate/report`, `/generate/prep`, and
   `/generate/letter` pull the user's recent entries and call the matching
   service, which calls `llmClient.js`.
4. Reports and letters are persisted (`reports`, `letters` tables); prep
   sheets are generated on demand and not stored.
5. `/anchor` (optional, per-report) is a 501 stub until the OnchainOS wallet
   step below is completed — once wired, it will write a hash of the report
   on-chain through the same shared Agentic Wallet used by the vault.

The **agent path** (via OKX A2MCP, once registered) skips steps 1–2 entirely
— OKX AI Marketplace handles who the caller is — and calls the step-3
services directly.

## What's in here

- `backend/` — Node/Express API on Railway. Owns the LLM calls, Postgres,
  the demo rate limiter, and the wallet/vault logic.
- `frontend/` — Next.js app on Vercel. Landing page with the no-wallet demo,
  plus a bare-bones `/dashboard` for testing the signed-in loop.

## Getting this onto GitHub without a terminal

1. Create a new empty repo on GitHub (no README, no .gitignore, so there's
   nothing to conflict with).
2. On the repo page, use **Add file → Upload files**.
3. Drag the `backend` and `frontend` folders in from your downloads (Chrome
   and Edge support dragging whole folders into that upload box). Commit.
4. If GitHub's uploader balks at nested folders, upload `backend` in one
   commit and `frontend` in a second commit, both to the repo root.

## Deploying the backend (Railway)

1. New Railway project → Deploy from GitHub repo → pick this repo → set the
   root directory to `backend`.
2. Add a Postgres plugin to the project. Railway sets `DATABASE_URL`
   automatically.
3. Set the remaining env vars from `backend/.env.example`: `LLM_BASE_URL`,
   `LLM_API_KEY`, `LLM_MODEL`, `JWT_SECRET`, `CORS_ORIGIN` (your Vercel URL,
   set this after step 2 of the frontend deploy below).
4. Set the start command if Railway doesn't infer it: `npm start`.
5. Once it's live, run the migration once. Easiest no-terminal way: add a
   one-off Railway "Deploy" with start command `npm run migrate` temporarily,
   or trigger it via Railway's web shell if your plan includes one. If
   neither is available, ask me and I'll add an `/admin/migrate` route
   gated by a secret header instead, so it can run over HTTP.

## Deploying the frontend (Vercel)

1. New Vercel project → import the same GitHub repo → set root directory to
   `frontend`.
2. Set env vars from `frontend/.env.example`: `NEXT_PUBLIC_API_URL` (your
   Railway backend URL) and `NEXT_PUBLIC_OKX_LISTING_URL` (fill in once the
   ASP listing exists).
3. Deploy. Go back to Railway and set `CORS_ORIGIN` to this Vercel URL.

## The one step that still needs a local session

Registering the ASP on OKX AI Marketplace requires running
`npx skills add okx/onchainos-skills` and creating the shared Agentic Wallet
through an agent session (Claude Code, Cursor, etc.). This only needs to
happen once, and the same wallet is shared with AgentPress. Do this in a
single local or cloud-shell session, then the backend calls the wallet over
its API from then on, no further local steps. Until this is done, `/anchor`
returns 501 and every `walletClient.js` method throws `NOT_WIRED` on
purpose, so the rest of the app never has to guess whether the wallet is
live.

## What v1 does and doesn't do

Does: report generation, appointment prep, advocacy letter drafts, read-only
prediction market info (labeled informational-only, no financial advice),
a principal-protected yield vault on the shared OKX Agentic Wallet, a
no-wallet demo on the landing page.

Doesn't do, by design, not just "not yet": prediction market wagering or
execution of any kind. `predictions.js` is a one-way read from Polymarket's
public API for display purposes only; nothing in the vault or `yield_pool`
tables can be spent against a market position.

Doesn't yet (deferred, see the product spec): on-chain anchoring (route
exists, returns 501 until the wallet is wired up), wearable sync,
multilingual or offline modes, the A2MCP handler itself (the route doesn't
exist yet — it will call the existing `src/services/*` functions once the
ASP is registered).
